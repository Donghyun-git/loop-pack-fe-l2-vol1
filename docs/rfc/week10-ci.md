# RFC — 10주차 CI: 검증을 기계에 새기기 전에, 무엇을 어떻게 잴지 먼저 정한다

> 이 문서는 측정 **전에** 작성을 시작했다. 0절의 사전 등록은 숫자를 하나도 보지 않은
> 상태에서 고정한 것이고, 그 이후 절은 측정이 끝나는 대로 채운다.
>
> 사전 등록을 먼저 쓰는 이유는 7주차와 같다. 기준을 나중에 고르면 어떤 결과든
> 성공으로 서술할 수 있고, 그렇게 쓴 글은 증거가 아니라 사후 해석이 된다.

## 0. 사전 등록 — 데이터를 보기 전에 고정한 것

### 0.1 합격 판정에 쓸 지표

| 지표               | 정의                                                | 역할                   |
| ------------------ | --------------------------------------------------- | ---------------------- |
| **job 창**         | job 의 `started_at → completed_at`                  | **판정값**             |
| run 창             | run 의 `run_started_at → updated_at` (큐 대기 포함) | 병기, 판정에 쓰지 않음 |
| step duration 합계 | 각 스텝 duration 의 합                              | **후보에서 제외**      |

판정값으로 job 창을 고른 이유는 러너 풀 대기 운이 판정에 섞이지 않게 하기 위해서다.
과제 문구는 "전체 wall-clock" 이므로, 지표를 바꿔치기했다는 반론이 생기지 않도록
run 창도 같은 표에 전부 싣는다.

step duration 합계를 후보에서 뺀 이유는 `Set up job` 과 `Post-*` 정리 스텝이 누락되기
때문이다. 이 레포의 과거 실행에서 그 둘만 합쳐도 약 5초이고, 이번에 노리는 개선폭과
같은 자릿수다. 즉 이 정의는 개선을 재는 자가 개선폭만큼 짧아지는 자다.

### 0.2 유의성 판정 규칙

**warm 쌍의 비중첩**으로 판정한다.

> After-warm 최댓값 &lt; Before-warm 최솟값

cold 쌍에는 적용하지 않는다. cold 는 "캐시 없는 브랜치의 첫 CI" 최악 케이스를 보여주는
서술 통계로만 싣는다.

"감소폭 &gt; 범위" 를 쓰지 않는다. n=3 에서 범위는 실제 산포를 체계적으로 **과소**추정하므로
그 규칙은 승리 선언 쪽으로 편향된다. 표본 3개가 정직하게 지지하는 주장은 분리 여부 하나뿐이다.

범위는 과제가 요구하므로 보고는 하되 판정에는 쓰지 않는다.

### 0.3 비중첩이 성립하지 않으면

그때는 아래 문장을 **결론으로** 쓴다. 헤드라인 주장 밑의 각주로 달지 않는다.

> 스텝 X 를 N초 줄였으나, job wall-clock 에서는 러너 노이즈를 넘는 차이로 보이지 않았다.

이 규칙을 지금 적어 두는 이유는, 결과를 본 뒤에 표현을 고르면 그것이 곧 사후 해석이기
때문이다.

### 0.4 표본 배제 규칙

- 실패·취소·타임아웃으로 끊긴 실행은 표본에서 제외하고 재실행한다.
  `pnpm check` 는 단축 평가 체인이라 중간에 실패하면 **더 짧은** wall-clock 이 나온다.
  이를 표본에 남기면 개선으로 오독된다.
- 적용한 전략이 캐시 계열이면, 전략 커밋 직후 1회차 실행은 캐시를 **채우는** 실행이므로
  폐기하고 2~4회차를 After 표본으로 쓴다.

### 0.5 측정 조건

| 조건        | 고정값                                                       |
| ----------- | ------------------------------------------------------------ |
| 이벤트      | `pull_request` 만 사용                                       |
| 재트리거    | Actions UI 의 "Re-run all jobs"                              |
| cold 생성   | **매 cold 실행 직전마다** 캐시 삭제                          |
| 표본당 기록 | SHA · 이벤트 타입 · cold/warm · run 창 · job 창 · conclusion |

cold 를 매번 만드는 이유는 성공한 실행이 끝에 캐시를 저장하기 때문이다. 묶음 앞에서
한 번만 지우면 2·3회차가 조용히 warm 이 된다.

과거 실행 9건의 42~95초 스프레드는 **노이즈 바닥으로 쓰지 않는다.** 그 표본은 서로 다른
커밋, cold/warm 혼재, 워크플로 내용 변경, 중간에 끊긴 실패 실행이 뒤섞인 이질 표본이다.
지터는 고정된 SHA 하나에서 같은 조건 3회로 새로 잰다.

### 0.6 SHA_BEFORE 의 정의

SHA_BEFORE 는 **`pnpm check` 를 5개 스텝으로 분리한 상태**다. 과거 실행들이 잰 워크플로가
아니다.

분리는 최적화가 아니라 계측이다. 분리 전 `pnpm check` 는
`pnpm test && pnpm lint && pnpm typecheck && pnpm build && pnpm test:e2e` 였고,
분리 후 5개 스텝은 같은 명령을 같은 순서로 실행한다. GitHub 이 각 스텝에 `if: success()`
를 암묵 적용하므로 `&&` 의 단축 평가도 그대로 재현된다. 실행되는 검증 셋·순서·중단 의미가
모두 동일하다.

`APP_ORIGIN` 은 분리 전 `Run quality checks` 한 스텝에 붙어 5개 명령 전부가 읽었으므로,
분리 후에는 job 레벨에 두어 같은 가시성을 재현한다.

분리하는 이유는 하나다. 합쳐 두면 Actions 가 보고하는 가장 긴 구간이 영원히
"Run quality checks" 한 덩어리라, 어느 명령이 병목인지 타임스탬프로 지목할 수 없다.

### 0.7 스모크 실행

12회 측정을 시작하기 전에 확인용 실행을 1회 돌린다. 이 레포에는 `pull_request` 이벤트로
실행된 기록이 한 번도 없어서, 아래가 전부 미검증 상태다.

- [ ] `pull_request` 트리거가 실제로 발동하는가
- [ ] 체크 런 이름이 무엇으로 렌더되는가 (branch protection 에 타이핑할 문자열)
- [ ] 캐시 적중/미적중 로그의 실제 문구
- [ ] cold 소요 시간 → `timeout-minutes` 값을 여기서 좁힌다

측정 예산의 1/12 로 위를 전부 확인한다.

## 2. 캐시 적중과 미적중

> 측정 후 작성. 적중 로그, lockfile 변경으로 만든 미적중 로그, 두 경우의 install 스텝
> 시간 차, 그리고 실험 후 lockfile 을 되돌린 기록.

---

## 3. 조건부 실행

> 실행 조건과 그 근거, 스킵이 안전한 이유(빈도와 분리해 서술), 조건에 걸리는 PR 과
> 안 걸리는 PR 의 로그, flaky 정책.

---

## 4. 예산 게이트와 환경 변수 검증

> 임계값과 그 근거, 초과 PR 의 빨간불과 PR 화면에 노출된 리포트, 환경 변수 게이트가
> 세 경우에 각각 실패하는 증거.

---

## 5. branch protection

> required 로 둔 것과, 별도 required 체크 이름을 만들지 않은 것들, 그리고 워크플로에
> 존재하지 않아 진짜로 제외된 것.

---

## 6. AI 코드리뷰

> 프롬프트 v1/v2, 지적 전체의 4분류 판정표, 잘 잡은 것 1건과 반증 가능하게 틀린 것 1건,
> 프롬프트 개선 근거, 순환성 명시.

---

## 7. 결정적 룰로 승격

> 승격한 룰과 그 근거 기록, 자가검증, 그리고 무엇을 AI·사람에 남기고 무엇을 기계로
> 내렸는지의 판단.

---

## 8. 워크플로 보안

> 최소 권한, third-party action 핀, `pull_request_target` 미사용, secrets 취급.
