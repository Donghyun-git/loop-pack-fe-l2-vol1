# RFC — 10주차 CI: 검증을 기계에 새기기 전에, 무엇을 어떻게 잴지 먼저 정한다

> 이 문서는 측정 **전에** 작성을 시작했다. 0절의 사전 등록은 숫자를 하나도 보지 않은
> 상태에서 고정한 것이고, 그 이후 절은 측정이 끝나는 대로 채운다.
>
> 사전 등록을 먼저 쓰는 이유는 7주차와 같다. 기준을 나중에 고르면 어떤 결과든
> 성공으로 서술할 수 있고, 그렇게 쓴 글은 증거가 아니라 사후 해석이 된다.

## 0. 사전 등록 — 데이터를 보기 전에 고정한 것

### 0.1 합격 판정에 쓸 지표

| 지표               | 정의                                                | 역할                   |
| ------------------ | --------------------------------------------------- | ---------------------- |
| **job 창**         | job 의 `started_at → completed_at`                  | **판정값**             |
| run 창             | run 의 `run_started_at → updated_at` (큐 대기 포함) | 병기, 판정에 쓰지 않음 |
| step duration 합계 | 각 스텝 duration 의 합                              | **후보에서 제외**      |

판정값으로 job 창을 고른 이유는 러너 풀 대기 운이 판정에 섞이지 않게 하기 위해서다.
과제 문구는 "전체 wall-clock" 이므로, 지표를 바꿔치기했다는 반론이 생기지 않도록
run 창도 같은 표에 전부 싣는다.

step duration 합계를 후보에서 뺀 이유는 `Set up job` 과 `Post-*` 정리 스텝이 누락되기
때문이다. 이 레포의 과거 실행에서 그 둘만 합쳐도 약 5초이고, 이번에 노리는 개선폭과
같은 자릿수다. 즉 이 정의는 개선을 재는 자가 개선폭만큼 짧아지는 자다.

### 0.2 유의성 판정 규칙

**warm 쌍의 비중첩**으로 판정한다.

> After-warm 최댓값 &lt; Before-warm 최솟값

cold 쌍에는 적용하지 않는다. cold 는 "캐시 없는 브랜치의 첫 CI" 최악 케이스를 보여주는
서술 통계로만 싣는다.

"감소폭 &gt; 범위" 를 쓰지 않는다. n=3 에서 범위는 실제 산포를 체계적으로 **과소**추정하므로
그 규칙은 승리 선언 쪽으로 편향된다. 표본 3개가 정직하게 지지하는 주장은 분리 여부 하나뿐이다.

범위는 과제가 요구하므로 보고는 하되 판정에는 쓰지 않는다.

### 0.3 비중첩이 성립하지 않으면

그때는 아래 문장을 **결론으로** 쓴다. 헤드라인 주장 밑의 각주로 달지 않는다.

> 스텝 X 를 N초 줄였으나, job wall-clock 에서는 러너 노이즈를 넘는 차이로 보이지 않았다.

이 규칙을 지금 적어 두는 이유는, 결과를 본 뒤에 표현을 고르면 그것이 곧 사후 해석이기
때문이다.

### 0.4 표본 배제 규칙

- 실패·취소·타임아웃으로 끊긴 실행은 표본에서 제외하고 재실행한다.
  `pnpm check` 는 단축 평가 체인이라 중간에 실패하면 **더 짧은** wall-clock 이 나온다.
  이를 표본에 남기면 개선으로 오독된다.
- 적용한 전략이 캐시 계열이면, 전략 커밋 직후 1회차 실행은 캐시를 **채우는** 실행이므로
  폐기하고 2~4회차를 After 표본으로 쓴다.

### 0.5 측정 조건

| 조건        | 고정값                                                       |
| ----------- | ------------------------------------------------------------ |
| 이벤트      | `pull_request` 만 사용                                       |
| 재트리거    | Actions UI 의 "Re-run all jobs"                              |
| cold 생성   | **매 cold 실행 직전마다** 캐시 삭제                          |
| 표본당 기록 | SHA · 이벤트 타입 · cold/warm · run 창 · job 창 · conclusion |

cold 를 매번 만드는 이유는 성공한 실행이 끝에 캐시를 저장하기 때문이다. 묶음 앞에서
한 번만 지우면 2·3회차가 조용히 warm 이 된다.

과거 실행 9건의 42~95초 스프레드는 **노이즈 바닥으로 쓰지 않는다.** 그 표본은 서로 다른
커밋, cold/warm 혼재, 워크플로 내용 변경, 중간에 끊긴 실패 실행이 뒤섞인 이질 표본이다.
지터는 고정된 SHA 하나에서 같은 조건 3회로 새로 잰다.

### 0.6 SHA_BEFORE 의 정의

SHA_BEFORE 는 **`pnpm check` 를 5개 스텝으로 분리한 상태**다. 과거 실행들이 잰 워크플로가
아니다.

분리는 최적화가 아니라 계측이다. 분리 전 `pnpm check` 는
`pnpm test && pnpm lint && pnpm typecheck && pnpm build && pnpm test:e2e` 였고,
분리 후 5개 스텝은 같은 명령을 같은 순서로 실행한다. GitHub 이 각 스텝에 `if: success()`
를 암묵 적용하므로 `&&` 의 단축 평가도 그대로 재현된다. 실행되는 검증 셋·순서·중단 의미가
모두 동일하다.

`APP_ORIGIN` 은 분리 전 `Run quality checks` 한 스텝에 붙어 5개 명령 전부가 읽었으므로,
분리 후에는 job 레벨에 두어 같은 가시성을 재현한다.

분리하는 이유는 하나다. 합쳐 두면 Actions 가 보고하는 가장 긴 구간이 영원히
"Run quality checks" 한 덩어리라, 어느 명령이 병목인지 타임스탬프로 지목할 수 없다.

### 0.7 스모크 실행

12회 측정을 시작하기 전에 확인용 실행을 1회 돌린다. 이 레포에는 `pull_request` 이벤트로
실행된 기록이 한 번도 없어서, 아래가 전부 미검증 상태다.

- [ ] `pull_request` 트리거가 실제로 발동하는가
- [ ] 체크 런 이름이 무엇으로 렌더되는가 (branch protection 에 타이핑할 문자열)
- [ ] 캐시 적중/미적중 로그의 실제 문구
- [ ] cold 소요 시간 → `timeout-minutes` 값을 여기서 좁힌다

측정 예산의 1/12 로 위를 전부 확인한다.

## 1. Before/After 측정

### 1.1 원시값 — Before (SHA_BEFORE `a50de2b`)

전부 같은 PR 의 `pull_request` 이벤트, "Re-run all jobs" 로 재트리거했다.

| 시도 | 조건 | job 창 (s) | conclusion | 비고                                  |
| ---- | ---- | ---------- | ---------- | ------------------------------------- |
| #1   | warm | 85         | success    |                                       |
| #2   | warm | ~~104~~    | success    | **배제** — debug 로깅을 켜고 실행했다 |
| #3   | warm | 106        | success    |                                       |
| #4   | cold | 89         | success    |                                       |
| #5   | cold | 94         | success    |                                       |
| #6   | cold | 88         | success    |                                       |
| #7   | warm | 102        | success    |                                       |

**#2 를 배제한 근거.** debug 로깅은 알려진 조건 변경이고, 그 영향이 스텝별로 드러난다.
`Set up pnpm` 이 18초로 다른 실행(3~~4초)의 4~~5배인데, 같은 실행의 `run:` 스텝들은
오히려 #1 보다 빨랐다(Unit 6 vs 9, Build 7 vs 8). debug 는 툴킷의 `core.debug` 를
내부에서 호출하는 **액션 스텝**을 부풀리고 셸 명령은 거의 건드리지 않는다. 느려서
버린 것이 아니라 조건이 달라서 버렸다 — 0.4 절의 배제 규칙은 성공 여부만 다루므로,
이 배제는 규칙의 확장이며 그 사실을 여기 적는다.

**cold/warm 라벨의 증거.** 로그 캡처가 아니라 API 의 스텝 타임스탬프로 판별된다.

| 스텝                   | warm (#1, #3, #7) | cold (#4, #5, #6) | 해석                          |
| ---------------------- | ----------------- | ----------------- | ----------------------------- |
| `Set up Node.js`       | 9, 11, 11         | 6, 5, 6           | warm 이 211MB 캐시를 복원한다 |
| `Install dependencies` | 2, 2, 2           | 4, 6, 7           | cold 가 store 를 새로 받는다  |
| `Post Set up Node.js`  | 0, 0, 0           | 5, 4, 4           | **cold 만 캐시를 저장한다**   |

`Post Set up Node.js` 가 warm 에서 0초, cold 에서 4~5초다. 캐시가 없었으니 끝에
저장한 것이고, 이 한 줄이 라벨의 기계적 증거가 된다.

### 1.2 요약 — Before

| 조건     | 원시값       | 중앙값 (job 창) | 범위            |
| -------- | ------------ | --------------- | --------------- |
| **cold** | 88, 89, 94   | **89**          | **88–94 (6)**   |
| **warm** | 85, 102, 106 | **102**         | **85–106 (21)** |

**run 창을 시도별로 남기지 못했다.** run 객체의 타임스탬프는 최신 시도만 반영하므로,
재실행으로 표본을 만들면 이전 시도의 run 창을 되찾을 수 없다. 최신 시도(#7) 기준
run 창은 107초이고 job 창 102초와 5초 차이다. 0.1 절에서 두 정의를 모두 싣겠다고
적었으나 재트리거 수단 때문에 지키지 못했고, 대신 판정값인 job 창은 전 표본에서
얻었다. 다음에 같은 측정을 한다면 `PR close → reopen` 을 쓰면 같은 SHA 로 새 run
객체가 생겨 시도마다 run 창이 남는다.

### 1.3 warm 이 cold 보다 느리게 나온 것에 대하여

warm 중앙값 102초가 cold 중앙값 89초보다 크다. 캐시를 쓰는 쪽이 더 느린 결과다.
스텝을 쪼개면 두 갈래로 갈린다.

캐시가 실제로 바꾸는 구간(중앙값):

| 조건 | `Set up Node.js` | `Install deps` | `Post Set up Node` | 합     |
| ---- | ---------------- | -------------- | ------------------ | ------ |
| cold | 6                | 6              | 4                  | **16** |
| warm | 11               | 2              | 0                  | **13** |

캐시가 아끼는 시간은 **3초**다.

캐시와 무관한 구간(중앙값):

| 조건 | Playwright | Unit | Build | E2E |
| ---- | ---------- | ---- | ----- | --- |
| cold | 23         | 8    | 8     | 18  |
| warm | 26         | 11   | 10    | 19  |

여기서 warm 이 9초 느리다. 캐시가 건드리지 않는 구간이므로 러너 변동이다.

**따라서 이 노이즈 수준에서 cold 와 warm 은 구분되지 않는다.** 캐시의 실제 효과
3초가 지터 6~21초에 묻힌다. 211MB 를 복원하는 비용이 새로 설치하는 비용과 거의
같다는 뜻이고, 이는 과제가 제시한 "setup-node·pnpm store 캐시" 전략이 이 레포에서
왜 더 얻을 것이 없는지를 설명한다.

### 1.4 병목 지목

유효 표본 6개의 스텝별 중앙값.

| 스텝                                        | 중앙값 (s) | job 창 대비 |
| ------------------------------------------- | ---------- | ----------- |
| **`Install Playwright Chromium when used`** | **23**     | **약 25%**  |
| `E2E tests`                                 | 18         | 19%         |
| `Unit tests`                                | 10         | 10%         |
| `Build`                                     | 9          | 9%          |
| `Set up Node.js`                            | 7.5        | 8%          |
| `Install dependencies`                      | 3          | 3%          |
| `Set up pnpm`                               | 3          | 3%          |
| `Checkout`                                  | 2          | 2%          |

**`Install Playwright Chromium when used` 가 단일 최장 구간이다.** cold 23초 /
warm 26초로 조건과 무관하게 같은 값이 나오는데, `~/.cache/ms-playwright` 는
캐시 대상이 아니므로 매 실행이 브라우저를 새로 받기 때문이다.

이 스텝은 이름이 "when used" 이고 `pnpm exec playwright --version` 가드를 갖고
있으나, `@playwright/test` 가 devDependency 라 가드가 항상 통과한다. 이름과 달리
무조건 실행되는 죽은 조건이다. 실제 조건부는 2단계에서 붙인다.

### 1.5 왜 이 전략만 골랐나

적용한 단일 전략: **`playwright install` 에 `--only-shell` 추가**.

`--dry-run` 으로 대조하면 받는 항목이 넷에서 셋으로 줄고, 빠지는 것이 정확히
풀 Chrome for Testing 바이너리다. `playwright.config.ts` 의
`devices['Desktop Chrome']` 는 1.62.1 에서 `channel` 을 지정하지 않으므로
(`channel: undefined`, `defaultBrowserType: 'chromium'`) headless 실행은
headless shell 로 뜬다. 따라서 설정 변경 없이 적용 가능하다.

**브라우저 바이너리를 캐시하지는 않았다.** Playwright 공식 문서가 권장하지 않는다 —
복원 시간이 다운로드 시간과 비슷하고, OS 의존성은 캐시 대상이 아니기 때문이다.
그리고 이 레포의 1.3 절 측정이 그 주장을 뒷받침한다. 211MB pnpm 캐시가 아낀 시간이
3초였다.

과제가 제시한 세 전략을 고르지 않은 이유:

| 전략                       | 기각 근거                                                                                                                                                                                                                 |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| setup-node·pnpm store 캐시 | **이미 적용되어 있다.** 게다가 1.3 절에서 그 효과가 3초로 측정되어 지터에 묻힌다.                                                                                                                                         |
| `concurrency` 그룹         | 측정은 같은 PR 에서 re-run 으로 돌므로 취소할 중복 실행이 없다. 걸어도 측정에 잡히지 않는다. ref 스코프 키의 근거는 8 절에 적는다.                                                                                        |
| job 병렬화                 | 프롤로그(checkout + pnpm + node + install)가 중앙값 약 17초인데 job 마다 중복 지불한다. 직렬 구간이 그보다 크지 않아 순손실이 유력하다. 또 job 을 쪼개면 required 체크 이름이 갈라져 2단계의 조건부 스킵 설계와 충돌한다. |

### 1.6 원시값 — After (SHA_AFTER)

> 측정 후 작성.

### 1.7 유의성 판정

> 0.2 의 규칙을 그대로 적용한 결과.
>
> 사전 전망: Before-warm 최솟값이 85초이므로, 비중첩이 성립하려면 After-warm 3회가
> 전부 85초 미만이어야 한다. 병목 스텝이 23초이므로 전부 없애도 경계선이다.
> 이 전망을 측정 전에 적어 둔다.

## 2. 캐시 적중과 미적중

> 측정 후 작성. 적중 로그, lockfile 변경으로 만든 미적중 로그, 두 경우의 install 스텝
> 시간 차, 그리고 실험 후 lockfile 을 되돌린 기록.

---

## 3. 조건부 실행

> 실행 조건과 그 근거, 스킵이 안전한 이유(빈도와 분리해 서술), 조건에 걸리는 PR 과
> 안 걸리는 PR 의 로그, flaky 정책.

---

## 4. 예산 게이트와 환경 변수 검증

> 임계값과 그 근거, 초과 PR 의 빨간불과 PR 화면에 노출된 리포트, 환경 변수 게이트가
> 세 경우에 각각 실패하는 증거.

---

## 5. branch protection

> required 로 둔 것과, 별도 required 체크 이름을 만들지 않은 것들, 그리고 워크플로에
> 존재하지 않아 진짜로 제외된 것.

---

## 6. AI 코드리뷰

> 프롬프트 v1/v2, 지적 전체의 4분류 판정표, 잘 잡은 것 1건과 반증 가능하게 틀린 것 1건,
> 프롬프트 개선 근거, 순환성 명시.

---

## 7. 결정적 룰로 승격

> 승격한 룰과 그 근거 기록, 자가검증, 그리고 무엇을 AI·사람에 남기고 무엇을 기계로
> 내렸는지의 판단.

---

## 8. 워크플로 보안

> 최소 권한, third-party action 핀, `pull_request_target` 미사용, secrets 취급.

## 9. 함께 생각해 볼 질문

> 네 질문에 각각 2~4문장.
